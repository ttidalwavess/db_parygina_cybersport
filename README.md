# Киберспортивная лига

База хранит данные о киберспортивных командах, их участниках, турнирах и матчах

| | |
| --- | --- |
| Главная таблица | Players |
| Связь N:M | Players и Teams через `data` |
| Бизнес-правило | Игрок одновременно только в одной команде |
| СУБД | PostgreSQL 17 в Docker |

## Как запустить

```bash
cp .env.example .env          # пароли и порт
docker compose up -d          # при первом запуске выполняются скрипты из db/
dbcheck run demo/lab1.sql     # сценарий лабы 1
```

Работа с базой: `docker compose exec db psql -U postgres -d app`. Сценарии выполняются в `psql` командой `\i /demo/lab1.sql`.

После изменения скриптов в `db/` базу нужно пересоздать: `docker compose down -v && docker compose up -d`.

Схема базы данных была доведена до 3НФ и следует ее требованиям: данные о командах, игроках, ролях и турнирах хранятся в отдельных таблицах; связующие таблицы содержат внешние ключи и атрибуты, относящиеся к соответствующим связям. Это позволяет избежать избыточного дублирования данных и аномалий при вставке, обновлении и удалении.


## Нормализация
**1. Исходная таблица без нормализации**

Изначально информацию о киберспортивной лиге можно представить в виде одной большой таблицы cybersport_data, которая содержит сведения об игроках, командах, ролях и турнирах.

| player_nickname | player_first_name | team_name | role_name | start_play | end_play | tournament_name | tournament_status | 
|-----------------|-------------------|-----------|-----------|------------|----------|-----------------|-------------------|
| Axiom | Alex | Team Spirit | carry | 2025-01-01 | 2025-06-01 | Winter Clash | completed |
| Dusk | Max | Team Spirit | support | 2025-01-01 | 2025-06-01 | Winter Clash | completed |

**2. Проблемы исходной таблицы**

**Избыточность данных:** Название команды Team Spirit и сведения о турнире Winter Clash повторяются в нескольких строках. Если у команды много игроков, её название будет записано многократно.

**Некорректность обновления:** Если название команды или статус турнира изменится, придётся исправлять несколько строк. Если одна строка останется без изменений, данные станут противоречивыми.

**Аномалия вставки:** Нельзя добавить новую команду или турнир, пока для них не существует записи об игроке, если все сведения хранятся в одной таблице.

**Аномалия удаления:** Удаление последней записи об игроке может привести к потере единственной информации о команде или турнире.

**3. Приведение к первой нормальной форме (1НФ)**

Каждое поле должно содержать одно значение, а повторяющиеся группы данных не должны храниться в одном поле. Например, сведения о нескольких игроках нельзя помещать в одну ячейку.

В проектируемой схеме каждый столбец содержит отдельное значение: никнейм, имя, название команды, роль или дату. Игроки, команды и турниры представлены отдельными записями.

**4. Приведение ко второй нормальной форме (2НФ)**

Для таблиц с составными первичными ключами неключевые атрибуты должны зависеть от всего ключа, а не только от его части.

В таблице `participating_teams` составной первичный ключ состоит из `teams_playing` и `contest_name`. Таблица хранит сам факт участия команды в турнире, поэтому отдельные сведения о команде и турнире в ней не дублируются.

В таблице `team_members` составной ключ включает `player_id`, `role_in_team`, `team_id`, `start_play` и `end_play`. Она описывает назначение игрока на роль в команде за определённый период. Данные об имени игрока, названии команды и названии роли хранятся в соответствующих таблицах.

**5. Приведение к третьей нормальной форме (3НФ)**

В третьей нормальной форме неключевые атрибуты не должны транзитивно зависеть от первичного ключа через другие неключевые атрибуты. Поэтому данные разделены на следующие таблицы:

`players` - имена игроков и уникальные никнеймы;
`teams` - названия команд;
`roles` - названия игровых ролей;
`tournaments` - названия турниров, даты проведения и статусы;
`team_members` - связь игроков, команд и ролей с указанием периода участия;
`participating_teams` - связь команд и турниров.

Название роли зависит от `roles.id`, а не от конкретного игрока. Каждая роль используется множеством игроков, их названия хранятся по одному разу в таблице `roles`, а остальные таблицы ссылаются на неё по внешнему ключу.

Аналогично, название команды хранится один раз в `teams`, а название турнира и его статус — в `tournaments`.

**Результат нормализации**

Разделение исходной таблицы на шесть связанных таблиц уменьшает избыточность данных, упрощает их обновление и обеспечивает ссылочную целостность с помощью первичных и внешних ключей. Связи между сущностями позволяют получать общую информацию о игроках, командах, ролях и турнирах с помощью SQL-запросов без многократного хранения одних и тех же описательных данных.


## Ограничения

| Ограничение | Таблица и колонки                     | Зачем                                                   |
|-------------|---------------------------------------|---------------------------------------------------------|
| `NOT NULL`  | roles: `role_name`    | Роль должна иметь название           |
|             | teams: `team_name`    | Команда должна иметь название           |
|             | players: `first_name, second_name, nickname`    | Игрок должен иметь непустые имя, фамилию, никнейм           |
|             | team_members: `player_id, role_in_team, team_id, start_play, end_play`    | База данных должна ссылаться на игроков по `player_id`, иначе она не сможет получить о нем данные           |
|             | tournaments: `tournament_name, start_day, end_day, status`    | Турнир должен иметь название, даты начала и окончания и статус           |
|             | participating_teams: `teams_playing, contest_name`    | База данных должна ссылаться на команды и турниры, иначе она не сможет получить о них данные           |
| `UNIQUE`    | roles - `role_name`                   | Роли не могут дублироваться                             |
|             | teams - `team_name`                   | Все команды должны быть разные                          |
|             | players - `nickname`                  | Игрок не должен содержаться в базе больше 1 раза        |
|             | tournaments - `tournament_name`       | Турниры не должны дублироваться                         |
| `CHECK`     | team_members: `start_play < end_play` | Старт карьеры не может произойти позже ухода из команды |
|             | tournaments: `start_day < end_day`    | Турнир не может начаться позже даты окончания           |
| `FOREIGN KEY` | team_members: `player_id`    | Ссылается на `id` из таблицы `players`           |
|               | team_members: `role_in_team`    | Ссылается на `id` из таблицы `roles`           |
|               | team_members: `team_id`    | Ссылается на `id` из таблицы `teams`           |
|               | participating_teams: `teams_playing`    | Ссылается на `id` из таблицы `teams`           |
|               | participating_teams: `contest_name`    | Ссылается на `id` из таблицы `tournaments`           |
